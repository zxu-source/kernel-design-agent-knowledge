## Upstream description

# DeepEP WheelNext Variant Wheel Build & Release

## 1. Background

### 1.1 WheelNext and PEP 817

[WheelNext](https://wheelnext.dev/) is the reference implementation of the Wheel Variant standard proposed in PEP 817. Traditional Python wheels express compatibility through platform tags (e.g., `manylinux_2_34_x86_64`), but cannot differentiate between hardware variants within the same Linux architecture (e.g., Ascend 910b vs a3). WheelNext injects **Variant Properties** into wheel metadata, enabling installers like pip/uv to automatically select the correct hardware-specific wheel based on the runtime environment.

### 1.2 Ascend Hardware Variant Detection

The [Huawei Ascend Variant Provider](https://github.com/wheelnext/huawei-ascend-variant-provider) is the WheelNext plugin for Ascend NPUs. It detects the NPU hardware type by parsing the `npu-smi` tool output from the CANN package and generates properties in the following format:

```
ascend :: npu_type :: <value>
```

Where `<value>` is the NPU type identifier:
- `910b` — Ascend 910B series (910B1 / 910B2 / 910B3 / 910B4)
- `a3` — Ascend 910_93 series

### 1.3 Motivation

Today, after installing deep_ep from PyPI, users must manually select the correct zip package based on their CANN version and NPU type. With WheelNext variants, a single command suffices:

```bash
uv pip install --system deep-ep --extra-index-url https://mirrors.huaweicloud.com/ascend/repos/pypi/variant
```

uv (wheelnext fork) automatically detects the local NPU hardware, resolves the variant index, and selects the matching wheel.

## 4. Build Pipeline Details

### 4.1 Stage 1: Compile the Wheel

Executed inside the CANN container image (`quay.io/ascend/cann:8.5.0-<hw>-ubuntu22.04-py3.11`):

```bash
./build.sh -a deepep2   # 910B
./build.sh -a deepep    # A3
```

Produces a `manylinux`-compatible deep_ep wheel (using `BinaryDistribution` with `has_ext_modules()=True`).

### 4.2 Stage 2: auditwheel repair

```bash
auditwheel repair "$whl" -w output/repaired/ \
  --exclude "libascend*.so" \
  --exclude "libtorch*.so" \
  --exclude libplatform.so \
  # ... 15 Ascend runtime libraries total
```

Bundles external dependencies (non-Ascend-runtime) into the wheel and retags it as `manylinux_2_34_<arch>`. The excluded `.so` files are provided by the target machine's CANN environment and are not packaged into the wheel.

### 4.3 Stage 3: Variant Property Injection

```
deep_ep-1.0.0-*.whl  ──►  variantlib make-variant  ──►  deep_ep-1.0.0-*-910b.whl
                         -f input.whl                     deep_ep-1.0.0-*-a3.whl
                         -o output/variants/
                         --property "ascend :: npu_type :: 910b"
                         --variant-label 910b
```

`make_variant.py` is a batch wrapper around `variantlib make-variant`. It:

1. Loads job configurations from `config.json`
2. Filters jobs by `variant_label` via the `-l` flag
3. Invokes `variantlib make-variant` for each job to inject hardware properties
4. Validates the variant metadata in the output wheel

**Key logic** (`make_variant.py:44-57`): The `-l` flag accepts either a directory or a single wheel file, automatically expanding all `.whl` files within a directory.

### 4.4 Hardware-to-Label Mapping

| Build Job | Hardware | `build.sh` arg | variant_label | Injected Property |
|-----------|----------|----------------|---------------|-------------------|
| `build_deep_ep_wheel_910b` | Ascend 910B | `-a deepep2` | `910b` | `ascend :: npu_type :: 910b` |
| `build_deep_ep_wheel_a3` | Ascend 910_93 | `-a deepep` | `a3` | `ascend :: npu_type :: a3` |

Note: 910b hardware maps to the `910b` variant label. This follows the Ascend NPU hardware generation naming convention:
- **910B series** = Ascend 910B1 / 910B2 / 910B3 / 910B4 (collectively "910b")
- **A3 series** = Ascend 910_93 ("a3")

### 4.5 Stage 4: Variant Index Generation and Publishing

```bash
# Merge all platform variant wheels
find all-wheels/ -path '*/variants/*.whl' -exec cp {} combined-variants/ \;

# Generate index.json
variantlib generate-index-json -d combined-variants/
```

Generated files are uploaded to Huawei Cloud OBS:

```
obs://ascend-artifcat-packages/pypi/packages/ascend/repos/pypi/variant/deep-ep/
├── deep_ep-1.0.0-*-910b.whl          # 910B variant wheel
├── deep_ep-1.0.0-*-a3.whl          # A3 variant wheel
└── index.json                       # Variant index
```

## 5. User Installation Flow

```bash
# 1. Install uv-wheelnext
curl -LsSf https://astral.sh/uv/install.sh | \
  sed 's/verify_checksum "$_file"/true/' | \
  INSTALLER_DOWNLOAD_URL=https://wheelnext.astral.sh/ sh
source $HOME/.local/bin/env

# 2. One-line install (uv auto-detects NPU type and selects the correct variant)
uv pip install --system deep-ep \
  --extra-index-url https://mirrors.huaweicloud.com/ascend/repos/pypi/variant
```

During installation, uv (wheelnext) will:
1. Call the `huawei-ascend-variant-provider` plugin to detect the local NPU type
2. Download and parse the variant index `index.json`
3. Select the variant wheel matching the local hardware
4. Install

## 6. Relationship with the Existing Build Pipeline

The upstream `build_and_release.yml` builds all packages (sgl_kernel_npu + torch_memory_saver + deep_ep + attentions), zips them, and publishes to GitHub Release. This workflow builds only deep_ep, using auditwheel + variantlib to produce WheelNext variant wheels published to OBS.

The two pipelines run independently and coexist in the short term. The long-term goal is to merge the WheelNext flow into the main build pipeline, at which point this workflow can be removed.
